# sm120 training optimization and integer experiments

2026-09-13. RTX 5060 Ti, 36 SMs, driver 615.71.09, existing 150 W power limit,
16 GB VRAM. No clock, power, driver-permission or desktop settings were changed.
These measurements are from a desktop GPU, not an isolated benchmark machine.

**The 95% peak target has not been achieved.** The optimized default preserves
the six-product compensated BF16 training math and the existing correctness
gates. Integer variants are experimental, not a recommended replacement.

## What changed

- Pack/transpose operands once per GEMM into one or three BF16 components.
  Reuse scratch buffers within the existing device memory cap.
- Custom 32×64×32 training tiles, four warps, `cp.async` 16-byte staging,
  skewed shared memory and `ldmatrix`. Inference uses 64×64×32 tiles.
  Interleave independent accumulators without changing each dot's summation
  order. Small matrices retain the original warp kernel.
- Parallel BN/LN forward/backward, layer-parameter reductions and masked
  policy/WDL loss, retaining double-precision reductions where needed.
- Query-parallel attention; backward separates score, Q/K/V and relative-bias
  reductions, removing contended atomics and the per-thread 361-float stack.
- Stop clearing unused host gradient mirrors during GPU graph reuse. Actual
  device gradients are still cleared before each backward pass.
- Retain `cuda-legacy` for A/B checks. It includes the common host-clear fix,
  so this comparison conservatively understates the total implementation gain.

All production math remains project-owned C/CUDA, dynamically compiled with
NVRTC; there is no cuBLAS, cuDNN, TensorRT or PyTorch dependency. HIP keeps its
existing kernels. The optional standalone benchmark needs `nvcc`/CUDA runtime.

## Measurements and the 95% denominator

The default C256/20-block model has 22,764,238 parameters and **10,801,677,312
useful matrix FLOPs per training example** (forward plus backward; FMA=2).
`gn_matrix_flops()` counts convolutions, projections and attention. It excludes
optimizer/non-matrix work, padding and precision-compensation products.

Representative matched run, full network, microbatch 16, 30 measured updates:

| Backend | Inference ms/batch | Training examples/s | Useful training matrix TFLOP/s |
| --- | ---: | ---: | ---: |
| Retained `cuda-legacy` | 60.3253 | 57.4153 | 0.620181 |
| Optimized `cuda` | 13.4348 | 219.724 | 2.37339 |

That run is **3.83× faster in training**. Other short runs varied with desktop
activity and clocks; do not interpret the extra digits as sustained guarantees.
Microbatch 64 measured 215.923 examples/s and 2,415,790,304 host tensor bytes;
it did not improve on microbatch 16 (877,219,808 host tensor bytes). Keep the
campaign's default microbatch 16: changing it also changes BN statistics.

The matrix diagnostic separately times packing plus GEMM and the already-packed
kernel. For the actual convolution-forward shape M=1296, N=256, K=2304, one
selected-tile run measured:

| Kernel | Kernel ms | Pack + kernel ms | Useful TFLOP/s, including pack | Executed BF16 TFLOP/s, kernel only |
| --- | ---: | ---: | ---: | ---: |
| Original six-product warp kernel | 1.11358 | 1.14439 | 1.33593 | 8.23732 |
| Tiled six-product kernel | 0.261995 | 0.410190 | 3.72711 | 35.4442 |

The selected training kernel was also measured on both backward shapes:

| Operation (M,N,K) | Kernel ms | Pack + kernel ms | Useful TFLOP/s, including pack | Executed BF16 TFLOP/s, kernel only |
| --- | ---: | ---: | ---: | ---: |
| Weight gradient (256,2304,1296) | 0.310074 | 0.335577 | 4.55581 | 29.9483 |
| Input gradient (1296,2304,256) | 0.223973 | 0.357905 | 4.27159 | 41.4612 |

The separate timed sections may run at different clocks. Executed operations
include six compensation products and padded tile work; useful operations do
not. Neither number is a hardware-counter utilization measurement.

NVIDIA distinguishes dense/sparse throughput and FP32/FP16 accumulation in its
[RTX Blackwell architecture tables](https://images.nvidia.com/aem-dam/Solutions/geforce/blackwell/nvidia-rtx-blackwell-gpu-architecture.pdf).
Using the GeForce BF16/FP32-accumulate rate of 512 FLOPs/SM/clock, 36 measured
SMs and the [5060 Ti's nominal 2.57 GHz boost](https://www.nvidia.com/en-us/geforce/graphics-cards/50-series/rtx-5060-family/)
gives an **inferred nominal dense reference of about 47.4 TFLOP/s**, not its
759 FP4 sparse AI TOPS headline. Its 95% target is approximately 45.0 TFLOP/s.
The forward kernel above is about 75% of that nominal reference (the input
gradient reached about 88%, still below 95%);
end-to-end useful matrix throughput is about 5%. Actual clocks/power alter
the instantaneous ceiling.

Six-product training has at most 1/6 of the single-product useful arithmetic
rate even before packing, padding, reductions and launch costs. Thus 95% of
single-product dense peak in **useful end-to-end training FLOPs** is incompatible
with this precision scheme. Achieving a high executed-instruction rate is a
different target and must not be presented as 95% model FLOP utilization.

`bench_sm120` also reports a register-only BF16/INT8 instruction issue probe.
It is labeled **not GEMM or training peak** and is not used as a utilization
denominator: clocks and the lack of memory/packing work make that misleading.
Nsight Compute returns `ERR_NVGPUCTRPERM`; permissions were not changed.
Nsight Systems timelines are usable. The original timeline attributed 54.1%
of GPU kernel time to GEMM, 20.7% to normalization, 9.3% to attention backward,
and 7.1% to the serial loss kernel. That motivated the non-GEMM changes too.

## Integer training assessment

The [PTX ISA](https://docs.nvidia.com/cuda/parallel-thread-execution/index.html#warp-level-matrix-instructions-mma)
provides signed INT8 warp MMA with INT32 accumulation on this target. The newer
`tcgen05` INT16-related instruction is not an sm120 instruction; its documented
target is sm107-family. The implementation uses original `mma.sync` INT8 code.

`cuda-int8` uses per-row symmetric max-absolute scales and round-to-nearest
signed INT8 operands. `cuda-int16` quantizes to [-32639,32639], decomposes each
value as `256*hi + lo` with signed bytes, and uses **four INT8 products**, not
a native INT16 Tensor Core instruction. INT32 reductions reset every K=32
to avoid overflow. Products are rescaled into FP32. Both paths apply to forward,
input-gradient and weight-gradient GEMMs; master weights, gradients, AdamW
moments, normalization, attention and loss remain floating point. Quantizer
derivatives are ignored (straight-through-style approximate gradients).

| Experiment | Observed accuracy | Decision |
| --- | --- | --- |
| INT8, C32 network | Policy relative L2 0.0272495, fails 0.01 gate | Not qualified |
| INT16-style, C32 | Policy 0.000111295; gradient 0.000226205; optimizer/checkpoint pass | Small-network pass only |
| INT16-style, full C256/20 | Global gradient relative L2 0.0613679, fails 0.001 gate | Not qualified |

The full INT16-style benchmark ran at 210.31 examples/s in one run, with no
saved weights, offering no clear advantage over the qualified default. Matrix
error alone (~2e-5 sampled relative L2 on the forward convolution shape) did not
predict the much larger full-network gradient difference. No convergence or
strength claim is made for either integer path. They print an experimental
warning and are not choices in the long-running campaign supervisor.

A future integer effort needs blockwise scales, outlier treatment, error
feedback/stochastic rounding, sensitive-layer mixed precision, and convergence
tests from identical checkpoints. Integer-only optimizer/nonlinear math and
compressed integer master weights are **not implemented**.

## Reproduce

From GEMM root (substitute an existing full-size checkpoint):

```sh
make -C nn -j4 all sm120-bench
nn/build/test_gpu cuda nn/build/cuda-wide.safetensors wide
nn/build/test_gpu cuda nn/build/cuda-full.safetensors full
nn/build/gn_tool bench MODEL cuda-legacy 16 30
nn/build/gn_tool bench MODEL cuda 16 30
# Forward, weight gradient, input gradient for the main 3x3 convolution:
nn/build/bench_sm120 1296 256 2304 0 1 50
nn/build/bench_sm120 256 2304 1296 1 0 50
nn/build/bench_sm120 1296 2304 256 0 0 50
# Tail and transpose tests: repeat with 0 0, 0 1, 1 0 and 1 1.
nn/build/bench_sm120 37 43 65 1 1 3
compute-sanitizer --tool memcheck --error-exitcode 1 \
    nn/build/test_gpu cuda nn/build/mem.safetensors wide
compute-sanitizer --tool racecheck --error-exitcode 1 \
    nn/build/test_gpu cuda nn/build/race.safetensors wide
# Explicit experimental paths; the full-network accuracy test is expected to fail:
nn/build/test_gpu cuda-int16 nn/build/int16-full.safetensors full
```

`gn_tool bench` uses ten inference and two training warm-ups; all updates are
in-memory, with no checkpoint mutation. JSON includes useful matrix FLOPs.
`bench_sm120` tests tail safety, both transpose flags, accumulated outputs,
all-output finiteness and 256 deterministic samples against a double-accumulate
CPU dot product. Its matrix tolerances are not a full-network training gate.

Verification includes the unchanged full-network gradient threshold, optimizer
and checkpoint tests, CUDA memory/race checks, HIP regression, native CPU tests,
the original PyTorch C4/C32 oracle and the tinyshogi self-play/replay pipeline.
Final CUDA C32 global gradient relative L2 was 0.0000014044431; the full model
was 0.00091501016. The C32 Compute Sanitizer runs reported zero memory errors
and zero race hazards. These are not exhaustive full-size memory/race sweeps.
Two effective-batch-256/microbatch-16 updates on our own full-model self-play
replay completed and saved a checkpoint, at 208.958 and 240.18 examples/s.
The first update matched the previous implementation's reported policy/value
losses (6.98197114 / 4.70389828) and pre-clip gradient norm (1131.05017).
The previously recorded correlated-input full-network FP32 stress discrepancy
is still outstanding: the selected implementation measured global gradient
relative L2 0.00731184111 against the 0.001 gate. These optimizations do not
resolve it.

Next performance work: multi-stage staging and shape-specific scheduling,
fused im2col/packing, cached weight packs with invalidation after updates,
CUDA Graph capture/multi-tensor optimizer launches, and measured counter-based
analysis when authorized access becomes available. No 95% acceptance claim,
long training campaign or trained-model promotion is made here.
Existing campaigns hash-pin their binaries; they intentionally reject an
in-place resume after this rebuild. Use a new run directory or an explicitly
audited migration, not edits that bypass that guard.

## BF16x3 and fused-convolution follow-up

The `cuda-bf16x3` backend uses high/high, high/low, and low/high BF16 tensor-core
products with FP32 accumulation.  On the full C256/20-block model at batch 16,
the strict CPU comparison passed with output relative L2 `3.4322599e-05` and
global-gradient relative L2 `0.00042316547`.  The optimizer and checkpoint
reload gates passed in the same run.

CUDA forward attention now groups eight queries per CTA and shares their K/V
tile.  Convolution forward additionally emits im2col directly into the two-plane
packed BF16 representation, eliminating the materialized FP32 column tensor and
its separate packing pass.  Three 100-step batch-16 runs measured 224.530,
230.134, and 230.681 examples/s in controlled before/after checks; three final
runs measured **230.134 examples/s median** (224.530--230.681).  Three batch-64
runs measured **238.694 examples/s median** (236.570--240.480), 2.57829 useful
matrix TFLOP/s, or **5.44%** of the card's 47.4-TFLOP/s nominal dense BF16/FP32
reference.  The 75%-of-peak target remains open.
