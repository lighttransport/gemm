# GLM-5.2 mixed-IQ runner on 12 A64FX nodes

This path runs `~/models/glm52-2bit` with the existing GLM-5.2 EP/TP graph. It
keeps routed-expert weights in their source IQ2_XS/IQ3_XXS/IQ4_XS formats,
assigns expert `e` to rank `e % 12`, and converts only dense rank-local TP slices
to BF16. No rank stores a second copy of another rank's expert or dense slice.

The source-format oracle is the local llama.cpp checkout at
`~/work/llama.cpp` (validated at `3debd0e31d3c`). `common/ggml_dequant.h`
implements the same IQ grids, signs, scales, and block layouts. Decode also has
an accuracy-preserving A16/SVE-SDOT implementation; the F32 row-dequant path is
the default because it benchmarks faster at the production thread count.

## 1. Convert once on shared storage

First inspect the size and tensor mapping without touching payload pages:

```sh
cd /vol0006/mdt0/data/hp250467/work/gemm/glm5-1
sh a64fx/glm5/convert_glm52_q2_ep12.sh --dry-run
```

The observed full-model estimates are 24.968 GiB for rank 0 and 23.447 GiB for
rank 11. The converter rejects any rank whose blob plus the 3 GiB runtime
reserve exceeds 29 GiB, and requires 27 GiB of free output space before
starting each rank. Convert all ranks sequentially:

```sh
sh a64fx/glm5/convert_glm52_q2_ep12.sh
```

Outputs go beside the checkpoint by default:
`~/models/glm52-2bit/a64fx-ep12-v1/rankNN.{blob,manifest}`. Conversion is
atomic and resumable: existing completed ranks are retained; use `--force` to
replace one. `GLM52_CONVERT_PARALLEL=1` is available only when shared-filesystem
bandwidth can tolerate twelve simultaneous readers.

For a bounded converter/loader test, use four layers and one rank:

```sh
GLM5_LAYERS=4 sh a64fx/glm5/convert_glm52_q2_ep12.sh --rank 0 --force
```

## 2. Stage and run inside the interactive 12-node allocation

The launcher discovers the 12-node Tofu topology, stages exactly one rank blob
per node to `/local/$USER/glm52-2bit-ep12`, builds the runner, and preserves a
complete run directory under `a64fx/glm5/logs/`.

**Arg-driven, no config env.** As of the 2026-07-18 refactor the runner
(`glm5_ep_runner`) takes every model/perf/generation knob as a `--flag`, and its
tuned 12n-Q2 production defaults are baked into the binary
(`glm5_bake_defaults()`): staged real weights, TP+EP12, q8 IQ expert kernels,
hoisted int8 dense (`--dense-i8`), lean bf16 all-reduce, `--maxpos 2304`,
`--pchunk 512`, auto KV tiering (`--cp-threshold 0`). Running with **no env and
no flags reproduces the tuned numbers**. Only a small set of *library-runtime*
env vars are still exported by the launcher because they must exist before the
process starts and cannot be program args — this is the documented boundary:
`FLIB_BARRIER=HARD`, `OMP_NUM_THREADS`/`OMP_PROC_BIND`/`OMP_PLACES`, and
`XOS_MMM_L_PAGING_POLICY`. Verify inside the job with `env | grep -E
'GLM5_|TP_|TF_'` (empty for a normal run) and `env | grep -E 'FLIB_|OMP_|XOS_'`.

```sh
# Four-layer distributed load/forward check
sh a64fx/glm5/run_glm52_q2_12n.sh check

# 2048-token prefill; acceptance gate 34 tok/s (override --prefill-target N)
sh a64fx/glm5/run_glm52_q2_12n.sh prefill

# 512-token prompt + 128-token greedy decode; gate 15 tok/s
sh a64fx/glm5/run_glm52_q2_12n.sh decode

# ~20 tok/s decode via reduced active experts (changes generated text)
sh a64fx/glm5/run_glm52_q2_12n.sh decode --active-experts 3

# faster prefill (issue-bound; banks the coarser group size)
sh a64fx/glm5/run_glm52_q2_12n.sh prefill --dense-i8-gs 256

# coding-agent usecase: ~108k-token system prompt -> generate code -> detokenize
sh a64fx/glm5/run_glm52_q2_12n.sh codegen
```

Any flag not consumed by the launcher (`--np`, `--last`, `--repeat`,
`--convert-dir`, `--stage-dir`, `--no-stage`, `--no-enforce`, `--prefill-target`,
`--decode-target`) is forwarded verbatim to `glm5_ep_runner` — see
`glm5_ep_runner --help` for the full flag list. The default `--convert-dir` is the
two-way expert-shard blobs `a64fx-ep12-2w-v1`.

The performance modes return nonzero when the rank-0 result misses the target;
`--no-enforce` disables the gate for diagnostic runs.

Staging uses 64 MiB `pread`/`pwrite` chunks, `fdatasync` every GiB, source and
destination `POSIX_FADV_DONTNEED`, and atomic rename. It is idempotent and never
copies all rank blobs on one node. `/local` is wiped between sessions, so the
default is to restage; pass `--no-stage` only after checking the current nodes.

Long context: `--ctx N` (alias for `--maxpos`) plus the auto KV tiering
(`--cp-threshold 0`, default) switches replicated bf16 KV (Tier A) to int4
CP-sharded KV + MSA (Tier B) once the budget is exceeded; cap Tier A with
`--kv-budget-gb N`.

## 5. Decode kernel campaign (2026-07-16, job 49604404): 1.24 -> 10.8+ tok/s

Root causes found (bench: `glm52_q2_kern_bench.c`, native, no MPI) and fixes, all
default-ON with env escapes:

1. **XOS prepage paging policy** put every heap page on the allocating thread's
   CMG: pure 48-thread SVE streaming read measured **94 GB/s**; with
   `XOS_MMM_L_PAGING_POLICY=demand:demand:demand` (now exported by the launcher)
   it is **843 GB/s**. All prior A64FX "bandwidth" conclusions (OMP-12 cap, pool
   uselessness, int8-GEMV-near-optimal) were artifacts of this. The runner's
   `--numa` interleave now masks to the CPU-bearing NUMA nodes (4-7) only.
2. **Decode attention was single-threaded** (`glm5_prefill_absorb_token`):
   163 ms/tok at ctx 640. New `glm5_absorb_token_par` (GLM5_ABSORB_PAR=0
   reverts) tiles (head x pos-chunk) across all threads, widens bf16 KV inside
   the dot/axpy kernels, merges per-tile online-softmax partials flash-style:
   2014 -> 80 us/layer (25x), **8.1 ms/tok measured in-decode**.
3. **Mixed-IQ q8 v2 kernels** (GLM5_IQ_V2=0 reverts): in-register tile expansion
   (IQ2_XS u64 grid+signmask gathers, IQ3_XXS u32 grid gather, IQ4_XS nibble
   TBL), SDOT + 16-lane scale MLA, ONE reduction per row. 47T [2048x6144]:
   IQ2_XS 225 Gw/s (5.2x), IQ3_XXS 184 (7.0x), IQ4_XS 198 (8.6x). Experts
   172.5 -> 12.5 ms/tok. Trap: scale vectors must be built in the SIMD domain
   (ld1ub+zip1 per block + per-tile TBL); svdupq-from-GPR per tile is SLOWER
   than the v1 scalar kernel.
4. **GLM5_PAR_MIN 512 -> 64** (env): 171-row shared slices and the 256-row
   router gate ran serial (67 us vs 16 us parallel).
5. **TP_AR_ROBUST=2** (lean AR) is now the launcher decode default (bitwise
   identical, small win).
6. **GLM5_DEC_FUSED=1**: two OpenMP regions per layer (barrier-staged workers)
   instead of ~10 parallel-for launches.  Measured ~neutral overall (region
   entry + barrier are only ~5 us each once measured properly; experts -1.6 ms,
   qkv +0.9) — kept because it makes the layer's sync structure explicit and
   marginally wins.  The real residual dense cost is COLD-STREAM bandwidth:
   each layer's weights are re-streamed from HBM every token at ~150-200 GB/s
   effective (the tight-loop 400+ GB/s bench numbers are partially L2-warm).

Measured ladder (512+128 single-stream, 12n): 1.24 (baseline ref path) -> 2.12
(q8 experts, prior session) -> 10.59 (fixes 1-4) -> 10.81 (5) -> **10.86 (6)**
tok/s, NaNs=0, decode GEN_IDS identical across runs A/B/D (the fused path is
numerics-preserving), comm ~35 ms/tok of the ~92 ms wall.

Dead ends measured (both env-gated OFF; do not re-try without new kernels):
- `GLM5_DENSE_I8=1` w8a16-f32 path (run C): wash. The M=1 w8a16 kernel is
  convert-bound at ~4x worse per-byte than the bf16 8-row kernel once paging is
  fixed (head 0.52 -> 1.18 ms).
- `GLM5_DENSE_I8=1 GLM5_MV_SDOT=2` int16-SDOT (run E): **8.55 tok/s, worse**.
  Standalone it does 457 Gop/s, but the path quantizes the ACTIVATION per call
  (~50 us serial); decode's small GEMVs (171-2048 rows) can't amortize it
  (shared 6.0 -> 17.1 ms/tok).  Fixable only by hoisting a shared per-stage
  activation quant across the GEMVs that consume the same vector.

Remaining walls at ~92 ms/tok: comm ~35 ms (dominated by expert-count skew:
top-8 of 256 over 12 EP ranks leaves ranks with 0..3 owned experts per layer;
the AR absorbs the imbalance as wait) and ~35 ms of cold-stream dense GEMV.

## 6. 2-way expert shard + hoisted-a16 int8 dense (2026-07-16 evening)

Both structural steps were implemented and measured:

1. **2-way expert shard** (`--shard2` in `glm52_gguf_convert.c` / `GLM52_SHARD2=1`
   in the convert script; manifest gains `# expert_shard 2`, loader autodetects).
   Half h of expert e lives on rank (e+h*ep/2)%ep: gate/up keep inter rows
   [h*1024,+1024), down keeps the matching inter COLUMNS (256-block aligned), so
   each half's swiglu/down partial is complete and the existing route AR sums the
   two halves — zero new communication.  Slot mapping is pure formula
   (`glm5_ex_slot`); all expert consumers read inter dims off the tensor
   (`ex_w1[s].rows`).  Blobs: `a64fx-ep12-2w-v1` (24.5 GiB/rank; 12-way parallel
   conversion via `GLM52_CONVERT_PARALLEL=1` took 27 min).
   Result: **comm 34 -> 24 ms/tok** exactly as designed, but wall only -1.2 ms —
   the freed AR slack exposed other skew (attention's 6-vs-5 heads, +2.7 ms of
   per-unit barrier chains). 11.00 tok/s.
2. **Hoisted-a16 int8 dense** (`GLM5_DENSE_I8=1` + fused-path a16 workers): ONE
   `glm5_a16_quantize` per stage on tid 0, `glm5_i16_worker` over the int16-SDOT
   8-row kernel for q_a/kv_a/q_b/o/shared.  Fixes the run-E per-call-quant trap.
   **11.62 tok/s** (qkv 20.3 -> 16.0, shared 7.0 -> 5.6).
3. **Batched expert units** (`glm5_exb_*`: all owned (expert,half) units in one
   pair pass + one accumulate-down pass, 4 barriers/layer; `GLM5_EXB=0` restores
   the per-unit loop): experts 14.2 -> 11.5-11.7 ms/tok and, once two runs of
   transient fabric noise cleared (o_proj AR wait spiked 11 -> 31 ms on two
   consecutive runs, then vanished — same binary), **13.37 tok/s** with comm at
   17.8 ms/tok, the lowest measured.

Ladder: 1.24 -> 10.86 (kernel campaign) -> 11.00 (2w shard) -> 11.62 (+ hoisted
a16 int8 dense) -> **13.37 tok/s** (+ batched expert units), NaNs=0 throughout.
Run-to-run variance on this allocation is large (8.5-13.4 for the same binary,
driven entirely by the o_proj-AR wait) — judge configs by their best-of-2/3, and
re-baseline after any allocation change.  Wall at best: 74.8 ms/tok = 61 compute
+ 17.8 comm.  15 tok/s needs ~8 ms more: qkv (16 ms, still ~2.5x its stream
floor), attention head imbalance, and the AR floor (~158 ARs x ~60-100 us,
12-rank recursive doubling pof2=8+4).

Best-config invocation (13.37 tok/s measured):

## 10. Fused-batch spec-verify campaign (2026-07-17, job 49610053): 9.19 -> 13.63 effective tok/s

Target was 20+ effective single-stream via the K=1 MTP verifier (M=2 batched
step).  The M=2 fused layer (`GLM5_BD_FUSED=1`) went from 137 -> 104 ms/step by
instrumenting per-stage (`GLM5_BD_TRACE=1`, the p1-trace analog — the PROFILE
buckets mislocated every problem) and fixing, in order:

- **tid0-serial activation work** (the batch path had kept scalar/serial
  norm+quant chains everywhere the single fused path had already parallelized):
  per-token norm->quant->group-sums chains spread across threads, gate matvec
  overlapped with the quant chains on disjoint thread ranges.
- **Scalar `glm5_quantize_i16_acts`** (same disease as the §9 scalar rmsnorm,
  one level deeper): every batched int16 GEMM entry quantized 6144 floats with
  scalar `lrintf`, ~25-30 us/row on one core.  Replaced with the SVE
  `glm5_a16_quantize` form (svrintn is bit-identical to lrintf here).
  norm+q 76 -> 10, nq2 28 -> 6, pn+gate 86 -> 41, route 51 -> 41 us/layer.
  This also feeds `glm5_gemm_int16sdot`, so legacy dense layers and prefill
  benefit too.  Biggest single win of the campaign: 11.9 -> 13.6.
- **Serial qfull/merge in the batch absorb** (attn bucket 15.9 -> 8.0 ms/tok).
- **exbN batched expert units**: the per-hit-slot 6-barrier chain became one
  4-barrier all-thread pass over flattened (slot, bucket-entry) units
  (experts 279 -> 244 us/layer; the cross-rank balance also cut the route-AR
  wait 333 -> 295).
- **abs2 shared-KV 2-query absorb** (`glm5_dot4x2_f32_u16`): the verify pair is
  same-stream consecutive positions, so both queries ride ONE KV stream with
  per-query causal limits (absorb 142 -> 112 us/layer).

Measured NULLS / LOSSES (all reverted or parked):
- SVE-izing the AR's scalar bf16 pack/reduce loops: decode-size ARs are
  round-latency-bound (~30 us/round; fp32 vs bf16 differs by only 2 us).  Kept
  for the large prefill payloads where the pack IS megabytes.
- `TP_AR_A2A=1` direct all-to-all (fp32, 1 round): oAR 97 -> 171 us — 11
  serialized puts + doubled payload lose to 3 bf16 recursive-doubling rounds.
- Batched N=2 dense GEMM forms: BOTH the dup-lane 4row_4x and a true
  `glm5_int16sdot_4row_2x` measured slower than two per-token 8-row matvecs
  (the 8-row kernel's prefetch schedule dominates the saved weight-widens).
- K=2 CHAINED MTP draft (M=3 verify, `GLM5_SPEC_K=2`): chained accept collapses
  (28%% blended vs 42%% for K=1) while the step grows 119 -> 145 ms.  Net loss
  at this context; the code stays for late-context retries.

Accept-rate CANNOT be A/B'd across numerics changes on ~100-step windows: any
bit-level change reroutes the greedy trajectory (39 -> 42 -> 27 -> 42%% across
benign changes).  Step time is the only stable optimization metric.

State at end of campaign (512+128, ctx ~640, this allocation):
plain decode 15.3 tok/s (65 ms/tok), spec-verify 13.63 effective
(104 ms/step, accept 42%%).  Step anatomy: ~64 ms compute (experts 244 us/L =
2x expert stream, intrinsic; absorb 112; qa+kv 110), ~30 ms ARs+skew (oAR 98 +
rAR 297 us/L; skew from per-rank expert-count imbalance), ~10 ms fixed (3
legacy dense layers, verify head, drafter).  The remaining floor analysis says
M=2 verify bottoms near ~88-90 ms -> break-even with plain needs accept >= 42%%
sustained; 20 tok/s needs accept >= 0.78 at K=1 — beyond this drafter at 512

### 10.1 The fused-path accept anomaly (open)

Paired on the same allocation/prompt, the K=1 verifier accepts 60.0%% through
the LEGACY batched path but only ~42%% through the fused path — worth +1.7
effective tok/s at the current step time.  `GLM5_BATCH_SELFCHECK2` (now also
prints an M=1 control) quantifies the fused-vs-legacy divergence:
rel_l2 = 8.3e-3 at M=1 and 2.0e-2 at M=2 (argmax still matches on the probe).
The M=1 divergence proves this is NOT an M=2-lane bug: the two paths use
different kernel/quantization mixes (e.g., legacy M=1 dense falls to the
f32-activation w8a16 kernel while fused always uses int16-SDOT activations;
gate matvec orderings differ), and the fused mix's extra activation noise is
enough to depress draft acceptance.  Since the drafter and all history run
through the single-token path, the verify path's noise directly corrupts the
hiddens the drafter sees.  Fused STILL wins effective (13.63 vs 12.11), so it
stays the default; recovering legacy-level accept at fused speed (+1.7 tok/s)
is the top open lead — bisect with `GLM5_BD_MAXL=<k>` (fused below k, legacy
above) and the selfcheck2 M1/M2 pair.

RESOLVED (2026-07-17, second campaign): TWO parts.  (1) the GATE kernel.  The

## 12. The 166-vs-407 GB/s GEMV gap: root-caused, NOT closed (2026-07-17)

Chasing section 11's lead (in-run dense GEMV 166 GB/s vs 407 for the identical
kernel/shape cold-standalone, 601 pure stream).  Four hypotheses died to
measurement; the mechanism is now known but no config recovers the bandwidth.

**Refuted, with the measurement that killed each:**
- **TLB / page-walk pressure**: A64FX/XOS pages are **64 KB**, so a 12 MB tensor
  is 192 pages. Non-issue. (`move_pages` histogram, `GLM5_NUMA_DBG=1`.)
- **Weight layout / prefetcher**: making the 8 rows of a block contiguous (ONE
  stream instead of 8) changed nothing (88.3 vs 89.2 us). The kernel's "8 short
  per-row streams under-run the HW prefetcher" comment and its 8x
  `__builtin_prefetch` chase a non-problem.
- **Kernel / issue cost**: `GLM5_DENSE_I8_GS` 64->128->256 is 1.34x/1.55x faster
  COLD but decode-neutral in-run (16.08/16.41/16.26).
- **glibc heap reuse defeating first-touch**: reproduced in a bench and it did
  NOT reproduce (372 GB/s either way).

**What is actually going on.** Placement, measured with `move_pages`:
1. `glm5_amalloc`'s `mbind(MPOL_INTERLEAVE)` **always fails EINVAL** — a `~0UL`
   nodemask sets bits for nonexistent nodes 8..63. It has never done anything.
2. The runner's process-wide `set_mempolicy(MPOL_INTERLEAVE)` (`glm5_apply_numa`,
   `--numa`/`GLM5_NUMA`, default ON) is what actually spreads weight pages — at
   the cost of making ~75% of every read cross the CMG ring. **166 GB/s is very
   close to one CMG's bandwidth** (calibrated: 1 CMG 160-180, 4 CMGs ~410).
3. Turning it off does not give locality: the loader copies each tensor with a
   **single-threaded memcpy**, so weights land wholly on the allocating thread's
   CMG (measured: `wq_a` 192/192 pages on node4; every IQ expert 27/27 on node4).

**The 2x2** (512+128, job 49630353, threads pinned in all four):

| XOS paging | placement | wq_a pages n4/n5/n6/n7 | qa+kva | decode |
|---|---|---|---|---|
| prepage (what actually runs) | interleave | 64/64/32/32 | 97.1 us | **16.24** |
| prepage | first-touch | **192**/0/0/0 | 178.0 | 13.39 |
| demand | first-touch (pinned) | 88/64/40/**0** | 107.0 | 15.55 |
| demand | interleave | 88/40/32/32 | **96.9** | 16.14 |

Interleave wins in BOTH paging modes; first-touch loses in both, because the
sub-threshold tensors (`wkv_a` 3.5 MB, every IQ expert ~1.6 MB) still land wholly
on one CMG even with a parallel copy. So the gap stands: interleave is ring-bound

### Is the GEMV compute- or TLB-bound? Null-kernel answer: COMPUTE (2026-07-18)

Per the user's suggestion, isolated with null kernels at a realistic 3-4 GB working
set (fresh mmap, first-touch, pinned, one region; scratch bw12/bw13/bw14). All
variants read EVERY weight byte in the SAME 8-row-block pattern as production:

| variant (3 GB, cold) | GB/s |
|---|---|
| pure HBM stream | ~890 |
| NULL-raw (u64 loads of the 8 rows, svadd) | 496 |
| NULL-widen (svld1ub_u16 widen, svadd — no svdot) | 451 |
| **SDOT-only (svdot_s64 chain, NO per-group scale)** | **442** |
| REAL kernel gs=256 | 208 |
| **REAL kernel gs=64 (production)** | **189** |
| NULL-interleaved (1 stream/8-row block) | 217 |

Conclusions:
1. **COMPUTE-bound, not TLB/memory.** The kernel's exact access pattern streams at
   451-496 GB/s; the real kernel is throttled to 189 purely by arithmetic.
2. **The svdot is NOT the cost** (SDOT-only = 442, near the ceiling). The throttle is
   the **per-group f64 scale-MLA**: `svcvt_f64_s64` + `svmla_n_f64` x8 rows + f64
   reductions, intrinsic to w8a16 group-quantized dequant. A64FX runs f64 at HALF the
   f32 rate. This is a ~2.3x tax (442 -> 189).
3. **Larger groups barely help** (gs=256 -> 208): it is the per-group f64 convert+MLA
   ops, not their frequency.
4. **Changing layout to cut TLB is REFUTED**: the interleaved single-stream layout is
   WORSE (217 < 496). The 8-interleaved-per-row-streams pattern is already good; the
   HW handles it near memory speed.

Can we make it memory-bound? The svdot already runs at memory speed; only the f64
scale-accumulate is in the way. Tried but did NOT work: naive f32 scale-accumulate
regressed to 119 GB/s (had to `svaddv_s64`-reduce each group to a scalar to leave the
f64 domain -> 768 reductions/tile vs the real kernel's 8; the real kernel's speed comes
from vector f64 accumulators reduced once). svdot_s64 forces int64 lanes -> f64 domain;
escaping to f32 needs a custom repack, uncertain payoff, and accuracy risk. The known
w8a8 path (svdot_s32, int8 activations) DOES hit ~440 GB/s but is lossy and already
measured a net decode loss (GLM5_GEMM_SDOT=1). So: compute-bound is confirmed and
localized to the w8a16 f64 dequant-accumulate; a faster accurate scale path is the one
real remaining kernel lever, and it is non-trivial. Note this affects only the DENSE
int8 GEMVs (qkv/o/shared/gate ~16-18 ms/tok); the 2-bit experts use different IQ
kernels.

### CORRECTION to the null-kernel numbers above: DCE-confounded (2026-07-18b)

The "SDOT-only = 442, NULL-widen = 451" figures in the compute-vs-TLB table were a
DEAD-CODE-ELIMINATION artifact: those micro-benches summed only 2 of the 8 output
rows into the sink, so the compiler eliminated the other 6 rows' work. Re-run with
ALL 8 outputs written to memory (scratch bw18-bw21, 1-3 GB cold, pinned):

| honest variant (8 rows written) | GB/s |
|---|---|
| pure stream, 1 contiguous/thread | 885 |
| raw8 (u64 load+add, 8 row-streams) | 208 |
| widen8 (svld1ub_u16+add, 8 streams) | 209 |
| **svdot-only, 8-row** | **208** |
| **REAL kernel (svdot + f64 scale + bias)** | **190** |
| interleaved layout (contiguous read) | 208 (1.09x) |
| R=1 row/block (fewest streams) | 167 |

Corrected conclusions:
- **The f64 scale-MLA epilogue costs only ~10%** (svdot-only 208 -> full 190), NOT the
  2.3x claimed above. So optimizing it cannot help much -- and indeed the properly
  implemented **f32-scale kernel is bit-accurate (rel_l2 = 3.7e-7, PASSES any gate) but
  gives NO speedup (0.98x)**: the epilogue is only 10% of the kernel, and within it the
  int64->float CONVERT (svcvt_*_s64, inherently 8-wide from svdot's int64 lanes)
  dominates, not the f64 multiply, so f32 changes nothing.
- **The real cap is the 8-concurrent-row-stream access pattern at ~208 GB/s** (vs 885 for
  a single contiguous stream). svdot-only already sits at that 208 cap -> the kernel is
  MEMORY-ACCESS-PATTERN bound (8 streams the HW prefetcher must track), not compute-bound
  and not TLB-bound.
- Tricks to beat the 208 cap all FAIL: interleaved weight layout recovers only 1.09x
  (contiguous addresses but the kernel still issues 8 sub-loads + 8 svdot per chunk);
  fewer rows/block (R=1, one stream) is WORSE (167) because per-row compute+xq-reload then
  dominates. The 8-row register-blocking that reuses the activation is already the sweet
  spot.

Net: the dense int8 GEMV is stuck at ~190 GB/s, bounded by the 8-row-stream memory pattern
plus a ~10% f64 epilogue. Neither f32, layout, nor stream-count changes move it materially.
The svdot int64->f64 path is intrinsic to accurate w8a16; the only faster route is lossy
w8a8 (svdot_s32, already a measured net decode loss). No cheap dense-GEMV win exists.
LESSON: any throughput micro-bench MUST consume every output (write to memory / sum all
lanes) or the compiler silently deletes rows and inflates GB/s 2-4x. Bit me twice here.

Tried the one untested bandwidth lever — the Fujitsu STREAM kernel

- **Contiguous layout doesn't help**: interleaved-layout svdot (contiguous read, 215) == row-major

blocking (R=1..8 all ~170-190), and now streaming prefetch (no gain). The only faster route is
lossy w8a8 (svdot_s32), already a measured net decode loss. No accuracy-preserving win exists.

## Prefill follow-up: 2-D BF16 work scheduling (2026-07-18)

The BF16 prefill GEMM parallelized only across 8-row output blocks.  That leaves
most cores idle for the TP-sharded router/shared gate/up matrices: the converted
12-rank manifests contain 256 rows on four ranks and 128 on eight (32 or 16 work
items on a 48-core node).  Exact-even shared slicing is 170--171 rows and also
left its 2--3 row remainder completely serial across all 512 tokens.

do not fill the node.  The auto selector minimizes `ceil(row_blocks*k/threads)/k`
for `k=1..4`, avoiding partially filled second waves; `GLM5_BF16_GEMM_SPLIT=0`
restores the old scheduling, and a positive value forces `k`.  The row remainder

unchanged; the dense qkv/o/shared buckets carry the improvement.

## Decode 20 tok/s opt-in: reduced active experts (2026-07-18)

`GLM5_ACTIVE_EXPERTS` overrides the checkpoint's top-8 MoE selection count at
runner startup.  The default remains 8: lowering it changes model semantics and
generated text, so this is an explicit speed/quality tradeoff rather than an
accuracy-preserving kernel optimization.

Controlled 12-node 512+128 runs used the production two-way expert shards,
`GLM5_DENSE_I8=1`, `GLM5_IQ_ROWN=0`, 47 threads, and the cache-line-aware W8A16
matvec:

| 8 (exact checkpoint) | 16.40--16.43 | 38.48--38.55 | 10.06 | 14.5 | exact baseline |
| 4 | 19.09 | 48.45 | 4.91 | 12.01 | below 20 |
| **3** | **20.09** | 52.39 | 3.96 | 10.71 | passes 20 |

An accuracy-preserving 8-way expert-slice experiment was also measured and

## 13. Arg-driven refactor + 256K long-context stability (2026-07-18)

The runner is now fully arg-driven (see §2): `glm5_bake_defaults()` bakes the
tuned 12n-Q2 knobs, `run_glm52_q2_12n.sh` exports only the FLIB/OMP/XOS runtime
boundary, and every model/perf/generation knob is a `--flag`. Verified zero-env
(job 49646685/49652133): `decode` 16.35-16.38 tok/s (== the §12 baseline),
`--active-experts 3` decode **20.18 tok/s**, `prefill --dense-i8-gs 256` **38.41
tok/s**, `check` NaNs=0. Decode is run-to-run nondeterministic (uTofu reduce
order + greedy attractor), so `--cp-threshold 0` (auto) was shown behaviorally
equivalent to legacy `-1` via identical tier-state logs + prefill argmax, not
GEN_IDS diff.

**256K prefill made stable.** The auto KV tiering fires cleanly
(`Tier A bf16 -> transition -> Tier B int4 CP-shard + MSA`), but the full 256K
prefill exposed a pre-existing **heap overflow in the MSA position gather**:
`glm5_msa_select` wrote `sel[nblk+nsel]` (a decode-only bitmap offset) into the
prefill's maxsel-wide `ms->psel` slice, overflowing once `nblk` (pos/128+1) grew
past the slack (nblk=2050 @256K > maxsel=2304). Rank 0 SIGABRT'd at teardown
after a numerically-correct full prefill. Fixed to apply the offset only when
`sel` aliases the bitmap buffer (`m->s_blk_sel`); a second latent overflow in the
batched `glm5_msa_prefill_select` (`bs` strided by `max_pos` instead of
`nblkmax`) was fixed too.

Result (job 49652133, layers=8, `--cp-threshold 2048 --pchunk 512
--set GLM5_MSA_BLOCK_REP=1`): full **262144-position prefill completes, NaNs=0,
315 tok/s, SENTINEL done, and the generation tail runs without aborting.**

Long-context operating notes:
- Full-fidelity 256K prefill is O(T^2) (the MSA index-scan is O(T)/token, ~4.6 h).
  `GLM5_MSA_BLOCK_REP=1` (one representative token scored per block) is the
  intended synthetic 1M-stress path and keeps prefill ~300 tok/s; it is a
  stability/stress tool, NOT for quality validation.
- Force the Tier A->B transition early (`--cp-threshold 2048`) so MSA sparse
  attention engages and prefill stays sub-quadratic; keep `--pchunk 512` so the
  transition fires after storing Tier-A positions (a pos-0 transition with a
  large pchunk hit an edge-case segfault).
- On 12 nodes a >~23k-token context exceeds the Tier-A bf16 KV budget, so any
  real long-context/coding-agent prompt (e.g. the 108k `codegen` prompt) runs
  through Tier B. KV save/load reuse across the tier boundary and full-fidelity
  (non-block-rep) long-context quality remain follow-ups.

## 17. Fixed-tree reduction follow-up (2026-07-21)

An opt-in `TP_AR_DETERMINISTIC=1` mode was added to `a64fx/utofu-tests/tp_allreduce.h`.
It uses a fixed-root binomial reduce followed by a reverse-tree broadcast for both SUM and
MAX, removing rank-order variation from BF16 all-reduces and CP/MSA block selection.  The
runner was rebuilt successfully and the mode is now printed in the `tp_ar` diagnostic.

Two full-weight 25.6K runs with fixed-tree SUM+MAX still differed after the first generated
token (`11` versus `23`), so collective rank order is not the sole source of the drift.
Two 8-layer 25.6K runs with the same fixed tree and `TP_AR_BF16=0` also differed, while
remaining NaN-free; FP32 transport reduced prefill from about 370 to 37 tok/s.  Thus FP32
collectives are a useful diagnostic only, not a production remedy.  The next stability lead
is local decode/prefill GEMM or Tier-B state-transition determinism, especially around the
first generated token after long-context prefill.

The runner now also accepts `--stable-outputs`, which composes fixed-tree collectives,
BF16 Tier-B KV, serial absorbed-MLA decode attention, and disables the lossy SDOT GEMM paths.
It leaves MSA selection unchanged; use `--set GLM5_MSA_BLOCK_REP=0` separately for the slower
full-block-scoring quality path.  This is an explicit stability profile; tuned performance
defaults are unchanged.

## 18. Stable-profile full-weight reruns and child-rank watchdog (2026-07-22)

The stable profile now also disables `GLM5_DENSE_I8`.  Keeping those 547 dense tensors in
BF16 avoids both a lossy decode path and the temporary BF16-plus-int8 conversion footprint
that caused earlier PLE SIGKILLs during model load.  A complete 78-layer load now uses about
24.9--26.1 GB per rank and has sufficient HBM headroom.

Two successful full-weight 25.6K runs with deterministic collectives, BF16 Tier B, all SDOT
paths disabled, dense int8 disabled, and serial absorbed attention remained NaN-free and
selected the same first token (`10938`).  They still diverged at token 2 (`16` versus
`79447`).  The same first-token-equal/token-2-different result reproduced twice at 4K, both
with stress block representatives and with full MSA block scoring.  Therefore neither
context length nor `GLM5_MSA_BLOCK_REP` explains the remaining autoregressive drift.

`--stable-outputs` now additionally serializes single-token OpenMP decode while leaving
chunked prefill parallel.  This is a correctness diagnostic and may substantially reduce
decode speed.  Its repeatability gate is pending because PLE retained a wedged rank-11 child
coordinate after the next load stall.

`run_glm52_q2_12n.sh codegen` now watches the per-rank load markers.  If all ranks have not
loaded within `--load-timeout` (300 seconds by default), it terminates the isolated MPI
process group instead of hanging forever and retries after a PLE teardown delay.  Recurrent
failures have consistently been 11/12 loads with rank 11 absent while HBM and writeback are
healthy.  PLE can retain coordinate `(0,0,0)` even after all local `mpiwrapp`, `org/mpiexec`,
and `plexec` processes are gone; when that happens a fresh allocation/session is required.
