# GLM-5.2 mixed-IQ runner on 12 A64FX nodes

This path runs `~/models/glm52-2bit` with the existing GLM-5.2 EP/TP graph. It
keeps routed-expert weights in their source IQ2_XS/IQ3_XXS/IQ4_XS formats,
assigns expert `e` to rank `e % 12`, and converts only dense rank-local TP slices
to BF16. No rank stores a second copy of another rank's expert or dense slice.

The source-format oracle is the local llama.cpp checkout at
`~/work/llama.cpp` (validated at `3debd0e31d3c`). `common/ggml_dequant.h`
implements the same IQ grids, signs, scales, and block layouts. Decode also has
an accuracy-preserving A16/SVE-SDOT implementation; the F32 row-dequant path is
the default because it benchmarks faster at the production thread count.

## 1. Convert once on shared storage

First inspect the size and tensor mapping without touching payload pages:

```sh
cd /vol0006/mdt0/data/hp250467/work/gemm/glm5-1
sh a64fx/glm5/convert_glm52_q2_ep12.sh --dry-run
```

The observed full-model estimates are 24.968 GiB for rank 0 and 23.447 GiB for
rank 11. The converter rejects any rank whose blob plus the 3 GiB runtime
reserve exceeds 29 GiB, and requires 27 GiB of free output space before
starting each rank. Convert all ranks sequentially:

```sh
sh a64fx/glm5/convert_glm52_q2_ep12.sh
```

Outputs go beside the checkpoint by default:
`~/models/glm52-2bit/a64fx-ep12-v1/rankNN.{blob,manifest}`. Conversion is
atomic and resumable: existing completed ranks are retained; use `--force` to
replace one. `GLM52_CONVERT_PARALLEL=1` is available only when shared-filesystem
bandwidth can tolerate twelve simultaneous readers.

For a bounded converter/loader test, use four layers and one rank:

```sh
GLM5_LAYERS=4 sh a64fx/glm5/convert_glm52_q2_ep12.sh --rank 0 --force
```

## 2. Stage and run inside the interactive 12-node allocation

The launcher discovers the 12-node Tofu topology, stages exactly one rank blob
per node to `/local/u14346/glm52-2bit-ep12`, builds the runner, and preserves a
complete run directory under `a64fx/glm5/logs/`.

```sh
# Four-layer distributed load/forward check
sh a64fx/glm5/run_glm52_q2_12n.sh check

# 2048-token prefill; default acceptance threshold is 34 tok/s
sh a64fx/glm5/run_glm52_q2_12n.sh prefill

# 512-token prompt + 128-token greedy decode; threshold is 15 tok/s
sh a64fx/glm5/run_glm52_q2_12n.sh decode
```

The performance modes return nonzero when the rank-0 result misses the target.
Override only for diagnostic runs with `GLM52_ENFORCE_TARGETS=0`; adjust explicit
gates with `GLM52_PREFILL_TARGET` and `GLM52_DECODE_TARGET`.

Staging uses 64 MiB `pread`/`pwrite` chunks, `fdatasync` every GiB, source and
destination `POSIX_FADV_DONTNEED`, and atomic rename. It is idempotent and never
copies all rank blobs on one node. `/local` is wiped between sessions, so the
default is to restage; set `GLM52_STAGE=0` only after checking the current nodes.

The production settings are TP+EP12, 24 prefill threads, 47 decode threads,
512-token prefill chunks, replicated BF16 KV for the 2304-position benchmark,
and exact dense attention (`GLM5_MSA=0`, `GLM5_CP=0`, `GLM5_INT4_KV=0`). Useful
overrides include `LAST=x,y,z`, `LLM_THREADS`, `GLM5_MAXPOS`, `GLM52_REPEAT`, and
`GLM52_RUN_DIR`.

## 3. Correctness gates

The mixed-IQ loader validates manifest type, shape, compressed byte count, and
every blob offset before constructing the model. The A16 decode kernel can be
checked directly against source-faithful F32 dequantization using a staged
four-layer rank blob:

```sh
GLM5_STAGE_DIR=/local/u14346/glm52-2bit-ep12 \
GLM5_LAYERS=4 GLM5_MAXPOS=32 GLM5_EP_RANK=0 GLM5_EP_SIZE=12 \
GLM5_TP=1 GLM5_CP_THRESHOLD=-1 GLM5_CP=0 GLM5_MSA=0 \
GLM5_IQ_SELFTEST=1 OMP_NUM_THREADS=48 \
  a64fx/llm/build/glm5_real_test
```

The bounded rank-0 IQ2_XS check measured `rel_l2=1.494e-05`,
`max_abs=6.628e-05`. Set `GLM5_IQ_REF=0` to use A16 SDOT in a runner experiment;
the default `GLM5_IQ_REF=1` retains the currently faster reference path. The
four-layer rank-local load/forward smoke gate also completed with `NaNs=0`.

## 4. Full-model result (2026-07-16, job 49598760)

All twelve blobs converted and validated (`287.450 GiB` total), then staged one
per node. The four-layer EP12 check passed with `NaNs=0` and measured 56.91
tok/s prefill / 57.98 tok/s decode.

The first untuned full-model prefill was 10.95 tok/s; enabling the established
48-thread, BF16-all-reduce, BF16-tok5 and optimized-attention defaults improved
it to **21.12 tok/s**. The 2048-token run completed with `NaNs=0`, but missed
the 34 tok/s gate. Its main buckets were experts 43.6%, shared expert 28.7%,
attention 12.4%, and communication 31.3% (overlapped percentages).

The tuned 512+128 single-stream run completed with `NaNs=0`: prefill 22.54
tok/s and decode **1.24 tok/s**, missing the 15 tok/s gate. Decode spent 38.9%
in routed experts, 36.7% in attention, 6.3% in the shared expert, and 45.6% in
20,224 all-reduce calls. These are measured gaps, not launcher target claims;
native mixed-IQ expert kernels and a structural decode communication/attention
reduction are still required to reach the requested goals.

## 5. Decode kernel campaign (2026-07-16, job 49604404): 1.24 -> 10.8+ tok/s

Root causes found (bench: `glm52_q2_kern_bench.c`, native, no MPI) and fixes, all
default-ON with env escapes:

1. **XOS prepage paging policy** put every heap page on the allocating thread's
   CMG: pure 48-thread SVE streaming read measured **94 GB/s**; with
   `XOS_MMM_L_PAGING_POLICY=demand:demand:demand` (now exported by the launcher)
   it is **843 GB/s**. All prior A64FX "bandwidth" conclusions (OMP-12 cap, pool
   uselessness, int8-GEMV-near-optimal) were artifacts of this. The runner's
   `--numa` interleave now masks to the CPU-bearing NUMA nodes (4-7) only.
2. **Decode attention was single-threaded** (`glm5_prefill_absorb_token`):
   163 ms/tok at ctx 640. New `glm5_absorb_token_par` (GLM5_ABSORB_PAR=0
   reverts) tiles (head x pos-chunk) across all threads, widens bf16 KV inside
   the dot/axpy kernels, merges per-tile online-softmax partials flash-style:
   2014 -> 80 us/layer (25x), **8.1 ms/tok measured in-decode**.
3. **Mixed-IQ q8 v2 kernels** (GLM5_IQ_V2=0 reverts): in-register tile expansion
   (IQ2_XS u64 grid+signmask gathers, IQ3_XXS u32 grid gather, IQ4_XS nibble
   TBL), SDOT + 16-lane scale MLA, ONE reduction per row. 47T [2048x6144]:
   IQ2_XS 225 Gw/s (5.2x), IQ3_XXS 184 (7.0x), IQ4_XS 198 (8.6x). Experts
   172.5 -> 12.5 ms/tok. Trap: scale vectors must be built in the SIMD domain
   (ld1ub+zip1 per block + per-tile TBL); svdupq-from-GPR per tile is SLOWER
   than the v1 scalar kernel.
4. **GLM5_PAR_MIN 512 -> 64** (env): 171-row shared slices and the 256-row
   router gate ran serial (67 us vs 16 us parallel).
5. **TP_AR_ROBUST=2** (lean AR) is now the launcher decode default (bitwise
   identical, small win).
6. **GLM5_DEC_FUSED=1**: two OpenMP regions per layer (barrier-staged workers)
   instead of ~10 parallel-for launches.  Measured ~neutral overall (region
   entry + barrier are only ~5 us each once measured properly; experts -1.6 ms,
   qkv +0.9) — kept because it makes the layer's sync structure explicit and
   marginally wins.  The real residual dense cost is COLD-STREAM bandwidth:
   each layer's weights are re-streamed from HBM every token at ~150-200 GB/s
   effective (the tight-loop 400+ GB/s bench numbers are partially L2-warm).

Measured ladder (512+128 single-stream, 12n): 1.24 (baseline ref path) -> 2.12
(q8 experts, prior session) -> 10.59 (fixes 1-4) -> 10.81 (5) -> **10.86 (6)**
tok/s, NaNs=0, decode GEN_IDS identical across runs A/B/D (the fused path is
numerics-preserving), comm ~35 ms/tok of the ~92 ms wall.

Dead ends measured (both env-gated OFF; do not re-try without new kernels):
- `GLM5_DENSE_I8=1` w8a16-f32 path (run C): wash. The M=1 w8a16 kernel is
  convert-bound at ~4x worse per-byte than the bf16 8-row kernel once paging is
  fixed (head 0.52 -> 1.18 ms).
- `GLM5_DENSE_I8=1 GLM5_MV_SDOT=2` int16-SDOT (run E): **8.55 tok/s, worse**.
  Standalone it does 457 Gop/s, but the path quantizes the ACTIVATION per call
  (~50 us serial); decode's small GEMVs (171-2048 rows) can't amortize it
  (shared 6.0 -> 17.1 ms/tok).  Fixable only by hoisting a shared per-stage
  activation quant across the GEMVs that consume the same vector.

Remaining walls at ~92 ms/tok: comm ~35 ms (dominated by expert-count skew:
top-8 of 256 over 12 EP ranks leaves ranks with 0..3 owned experts per layer;
the AR absorbs the imbalance as wait) and ~35 ms of cold-stream dense GEMV.

## 6. 2-way expert shard + hoisted-a16 int8 dense (2026-07-16 evening)

Both structural steps were implemented and measured:

1. **2-way expert shard** (`--shard2` in `glm52_gguf_convert.c` / `GLM52_SHARD2=1`
   in the convert script; manifest gains `# expert_shard 2`, loader autodetects).
   Half h of expert e lives on rank (e+h*ep/2)%ep: gate/up keep inter rows
   [h*1024,+1024), down keeps the matching inter COLUMNS (256-block aligned), so
   each half's swiglu/down partial is complete and the existing route AR sums the
   two halves — zero new communication.  Slot mapping is pure formula
   (`glm5_ex_slot`); all expert consumers read inter dims off the tensor
   (`ex_w1[s].rows`).  Blobs: `a64fx-ep12-2w-v1` (24.5 GiB/rank; 12-way parallel
   conversion via `GLM52_CONVERT_PARALLEL=1` took 27 min).
   Result: **comm 34 -> 24 ms/tok** exactly as designed, but wall only -1.2 ms —
   the freed AR slack exposed other skew (attention's 6-vs-5 heads, +2.7 ms of
   per-unit barrier chains). 11.00 tok/s.
2. **Hoisted-a16 int8 dense** (`GLM5_DENSE_I8=1` + fused-path a16 workers): ONE
   `glm5_a16_quantize` per stage on tid 0, `glm5_i16_worker` over the int16-SDOT
   8-row kernel for q_a/kv_a/q_b/o/shared.  Fixes the run-E per-call-quant trap.
   **11.62 tok/s** (qkv 20.3 -> 16.0, shared 7.0 -> 5.6).
3. **Batched expert units** (`glm5_exb_*`: all owned (expert,half) units in one
   pair pass + one accumulate-down pass, 4 barriers/layer; `GLM5_EXB=0` restores
   the per-unit loop): experts 14.2 -> 11.5-11.7 ms/tok and, once two runs of
   transient fabric noise cleared (o_proj AR wait spiked 11 -> 31 ms on two
   consecutive runs, then vanished — same binary), **13.37 tok/s** with comm at
   17.8 ms/tok, the lowest measured.

Ladder: 1.24 -> 10.86 (kernel campaign) -> 11.00 (2w shard) -> 11.62 (+ hoisted
a16 int8 dense) -> **13.37 tok/s** (+ batched expert units), NaNs=0 throughout.
Run-to-run variance on this allocation is large (8.5-13.4 for the same binary,
driven entirely by the o_proj-AR wait) — judge configs by their best-of-2/3, and
re-baseline after any allocation change.  Wall at best: 74.8 ms/tok = 61 compute
+ 17.8 comm.  15 tok/s needs ~8 ms more: qkv (16 ms, still ~2.5x its stream
floor), attention head imbalance, and the AR floor (~158 ARs x ~60-100 us,
12-rank recursive doubling pof2=8+4).

Best-config invocation (13.37 tok/s measured):

```sh
GLM5_DENSE_I8=1 \
GLM52_CONVERT_DIR=$HOME/models/glm52-2bit/a64fx-ep12-2w-v1 \
GLM5_STAGE_DIR=/local/u14346/glm52-2bit-ep12-2w \
sh a64fx/glm5/run_glm52_q2_12n.sh decode
```

## 7. MTP brought up end-to-end (2026-07-16 late; alpha measured, verifier too slow)

The UD-Q2_K_XL gguf ships the full layer-78 nextn block; `--mtp` in the
converter now emits it as `model.layers.78.*` (+ eh_proj/enorm/hnorm/
shared_head.norm; attention+shared REPLICATED, experts 2-way sharded like the
main layers).  Blobs: `a64fx-ep12-2wm-v1` (25.4 GiB/rank).  Runtime work to make
it real:

1. **MTP prefill back-fill** (was missing; alpha measured 0.0% because the draft
   block attended its own NEVER-WRITTEN KV for every prompt position): the
   runner now captures the last-layer residual of each prompt position (free —
   the prefill chunk buffer holds exactly that) and runs the drafter over the
   prompt once after prefill (~5-7 s one-time, lockstep collectives).
2. **The Q2_K/Q3_K mis-dispatch bug**: the nextn experts are K-quants (86 Q2_K +
   43 Q3_K), NOT the IQ formats; `glm5_mv_pair`'s q8 fast path and the fused
   expert workers gated only on `glm5_is_ggml_q()` and fed them to the IQ row
   kernels -> garbage -> all-NaN drafts (the constant argmax 12907 = NaN-argmax
   artifact at rank 1's head-shard base).  Fixed with exact-type guards
   (`glm5_iq_q8_ok`) + per-layer `ex_iqok`; unsupported types take the
   source-faithful dequant fallback (fine for a 1-layer drafter).

Measured (512+128, greedy): drafter TF over the prompt **30.0%**; decode
side-draft alpha **25.8% early-window / 63.7% full-generation** (strongly
context-dependent — the default SPEC_MIN_ALPHA_PCT=25 abort gate triggers on the
early window; disarm with GLM5_SPEC_WARMUP).

**K=2 verifier optimization campaign (job 49610053):** the M=2 batched step went
950 -> ~180 ms via three fixes to the batched path (all default-ON, useful for
bd=1 serving too): (1) small-N q8 IQ expert GEMMs incl. N==1 — the g=1 buckets
were silently falling to the scalar F32-dequant path, 330 ms/step
(`glm5_gemm_iq_q8_smalln`, ordered BEFORE the N<=1 early-out); (2) small-M
attention through the all-thread parallel absorb (was 2 threads x serial scalar
KV decode, 160 ms/step); (3) `GLM5_GEMM_SDOT=2` int16-SDOT GEMMs for the int8
dense (also lifts prefill 24.8 -> 30.0 tok/s).  Net spec-verify: **1.42 -> 8.27
tok/s** at 58% accept — still BELOW the 13.49 plain fused decode.

**Negative result — spec decode cannot beat plain decode on this sync
structure:** a fully fused-batch M=2 layer was built (`glm5_bd_layer_fused`,
weight-shared preq-int16 workers + q8 bucket workers + per-token parallel
absorb) and measured at the SAME ~180 ms/step: the ~30 barrier/serial syncs per
layer that the M=2 dataflow needs cost ~25-50 us each in-decode (same lesson as
the single-stream fusion — sync count is the floor, not kernel work).  Even at
the best measured accept (68%), a ~150-180 ms verify step yields ~11 tok/s < the
13.49 plain path.  `GLM5_BD_FUSED` defaults OFF (it also still has a small
numeric divergence vs the single path: accept 33% vs 58% through the legacy
batched path).  Spec decode on this machine needs either a fundamentally cheaper
sync (A64FX hardware barrier integration in the Fujitsu runtime, incompatible
with OMP_PROC_BIND today) or a much stronger drafter.

Batched decode (bd=1) already exists for multi-stream serving throughput and
benefits from fixes (1)-(3) directly.

## 8. 15 tok/s reached: the A64FX hardware barrier (2026-07-16, job 49610053)

Stage-level tracing of the fused phase 1 (`GLM5_P1_TRACE=1`) showed a ~25-40 us
FIXED cost on every barrier-delimited stage regardless of content (prefetch and
a fused group-sum quantizer were exact nulls) — the SOFTWARE barrier's
release/arrival stagger at 47 threads, ~150 us/layer across the fused stages.
`FLIB_BARRIER=HARD` (Fujitsu OMP runtime's A64FX hardware-barrier mode, now the
launcher default; it force-overrides OMP_PROC_BIND with a benign jwe1051i
warning, and requires no omp_set_num_threads calls) collapses it:

    attn 102.5 -> 78.3 us/L | qa+kva 103 -> 94.9 | qb 35 -> 26.7 | oq+o 48.5 -> 43.9

**Decode 13.3 -> 15.01 tok/s (512+128, NaNs=0), prefill 30.7 tok/s.**  Ladder:
1.24 -> 10.86 (kernel campaign) -> 11.00 (2-way expert shard) -> 11.62
(hoisted-a16 int8 dense) -> 13.37-13.49 (batched expert units) -> **15.01**
(hardware barrier).  Also relevant: the same hardware barrier should be
re-tried under the spec verifier (its ~30 syncs/layer were the measured floor)
and the single-fused/batched-fused comparisons deserve re-measurement, since
every earlier sync-cost conclusion was measured under the software barrier.

Best-config invocation is unchanged (section 6) — FLIB_BARRIER=HARD is now a
launcher default.

## 9. Post-15 wins: SVE rmsnorm + q8 prefill experts (both gates PASS)

- **SVE rmsnorm** (`glm5_rmsnorm_gemma/_head` were fully scalar, ~20-25 us per
  6144-vector on tid 0 — the largest serial-glue item in the phase-1 trace):
  norm+q 35.7 -> 9.4 us/layer, norm+q2 13.2 -> 4.2.
  **Decode 15.07 -> 16.53 tok/s** (gate PASS, 15.00).

  buckets (g~16-32 tokens/expert-unit) were taking the dequant-once F32 path
  whose scalar IQ dequant dominates; the q8 row kernels re-dot L1-hot weights
  per activation and win well past g=16.  Prefill experts 15.8 -> 9.5 ms/tok.
  **Prefill-only 2048 tok: 28.18 -> 36.23 tok/s** (gate PASS, 34.00; final
  argmax identical to the F32-path baseline).

  x3; robust 0/1/2 all equal), 78-AR token = 5.01 ms -> decode's 158 ARs have a

  receive-path work (per-round cost looks cache-maintenance-bound), a deeper

Current bests: **decode 16.53 tok/s, prefill 36.23 tok/s** (512+128 decode /
